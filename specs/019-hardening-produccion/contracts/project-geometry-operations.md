# Contract: Atomic project and geometry operations

**Scope**: US3, FR-017–FR-024, FR-041.
**Rule**: all mutation endpoints require authenticated admin, active workspace and `Idempotency-Key`.

## 1. Common idempotency envelope

Headers:

```http
Idempotency-Key: 1..128 printable characters
```

Server canonicalizes the accepted schema, computes SHA-256 and claims scope:

```text
organization + principal + operation type + resource scope + key
```

- first request: executes and stores resource/status;
- same key + same canonical payload: returns original status/body and header `Idempotency-Replayed: true`;
- same key + different payload: `409 IDEMPOTENCY_CONFLICT`;
- key propagates to RPC, audit and later repair; it is not regenerated by the server.

## 2. Create project with lots

`POST /api/projects`

Strict JSON:

```json
{
  "name": "Proyecto Piloto",
  "region": "Maule",
  "comuna": "Teno",
  "descripcion": "optional",
  "total_lotes": 53,
  "lotPrefix": "Lote",
  "precio": 25000000,
  "valor_reserva": 500000
}
```

`total_lotes` is an integer from 1 through 100 for the pilot. Zero, negative, fractional or larger values return `422 PROJECT_LOT_COUNT_LIMIT` before allocating a lot array or opening a transaction.

Unknown fields are rejected, including `id`, `organization_id`, audit fields, state, vendor assignments, raw Storage paths and `geometry_id`.

The server derives an exact lot plan (`numero`, defaults) and calls `create_project_with_lots`. Project, N lots, operation result and audit commit together.

Success `201` or replay `200`:

```json
{
  "operationId": "uuid",
  "project": { "id": "uuid", "name": "Proyecto Piloto", "total_lotes": 53 },
  "lots": { "count": 53, "ids": ["uuid"] }
}
```

Failure leaves zero new project/lots/audit-success rows. No TypeScript delete rollback is part of the contract.

## 3. Update project

`PATCH /api/projects/{projectId}`

Strict allowlist: `name`, `region`, `comuna`, `descripcion`, `precio`, `valor_reserva`. Files use the file gateway and are never accepted as images/doc fields, legal metadata arrays or paths in this patch; lot count changes use a separate explicit operation and are out of this patch.

Unknown/protected fields return `422 PROTECTED_FIELD`. The route scopes project to active organization before parsing business changes and writes audit atomically.

## 4. Import KMZ/KML

`POST /api/projects/{projectId}/geometry-imports`

The URL carries `projectId`; multipart contains exactly one bounded `file` part and the request carries `Idempotency-Key`. Session, active workspace, project scope, actor authorization, effective `canonical_geometry_import` control, declared-size check and rate/concurrency claim all happen before opening the multipart stream. OFF/fail-closed returns `503 FEATURE_DISABLED` without reading the file. Actual-byte limits are enforced while streaming, before decompression.

Baseline limits:

| Limit                |                    Value | Error code                  |
| -------------------- | -----------------------: | --------------------------- |
| compressed body      |                   20 MiB | `GEOMETRY_COMPRESSED_LIMIT` |
| expanded total       |                  100 MiB | `GEOMETRY_EXPANDED_LIMIT`   |
| ZIP entries          |                      100 | `GEOMETRY_ENTRY_LIMIT`      |
| per-entry ratio      |                     20:1 | `GEOMETRY_RATIO_LIMIT`      |
| features             |                    2.000 | `GEOMETRY_FEATURE_LIMIT`    |
| coordinate positions |                  250.000 | `GEOMETRY_COORDINATE_LIMIT` |
| XML depth/nodes/text |     64 / 500.000 / 8 MiB | `GEOMETRY_XML_LIMIT`        |
| processing deadline  |                     10 s | `GEOMETRY_TIMEOUT`          |
| concurrency          | 1 actor / 2 organization | `GEOMETRY_BUSY`             |
| rate                 | 10 organization / 10 min | `RATE_LIMITED`              |

Success:

```json
{
  "operationId": "uuid",
  "importId": "uuid",
  "sourceSha256": "hex",
  "status": "committed",
  "counts": { "features": 4, "coordinates": 80 },
  "features": [
    {
      "geometryId": "uuid",
      "sourceIndex": 0,
      "sourceHash": "hex",
      "geometryType": "lot",
      "name": "Lote 1",
      "assigned": false
    }
  ]
}
```

The source bytes are preserved through the private file gateway as category `geometry_source` under their content hash; `geometry_imports.source_file_id` references that immutable metadata. Upload/DB failure uses deterministic cleanup or a durable repair finding. The response may include normalized geometry needed by the assignment UI, within the same authorized request, but no duplicate DB write occurs later. Same content under another filename returns the existing import only while that import is active. If the content exists only in superseded history, a later replacement creates a new import-version row referencing the same immutable source object; it never reactivates or rewrites the old row. Same key/different bytes conflicts. Exact duplicate geometry+properties inside one source quarantines the whole attempt as `GEOMETRY_DUPLICATE_FEATURE`; same geometry with distinct approved semantic properties remains separate by source index.

`GeometryUploadPanel.tsx`, onboarding and geometry assignment consume only this URL and the returned `features[].geometryId`. `/api/uploads/geometry` is removed rather than retained as a fallback; disabling the control pauses new writes and never selects the legacy parser/writer.

## 5. Assign existing canonical geometry

`POST /api/onboarding/save-and-assign`

```json
{
  "projectId": "uuid",
  "geometryId": "uuid",
  "lotId": "uuid"
}
```

Raw GeoJSON is not accepted. RPC locks both rows and verifies same project/workspace, active import, unassigned geometry and empty lot. Commit includes:

```text
geometries.lot_id/is_assigned/area_m2/updated_at
lots.geometry_id/m2/updated_at
audit + idempotency result
```

Competing assignment returns `409 LOT_GEOMETRY_CONFLICT` with the winning resource ID only if visible to the same organization.

Servidumbre/deslindes transition to `pending`; a later worker/retry records `ready` or `failed` with cause. Assignment success never implies enrichment ready. Once the core assignment commits, the route returns `202` with an explicit split state instead of reporting request failure:

```json
{
  "assignmentStatus": "committed",
  "enrichmentStatus": "pending",
  "retryScheduled": true
}
```

## 6. Save derived infrastructure

`POST /api/onboarding/save-infrastructure`

```json
{
  "projectId": "uuid",
  "sourceGeometryIds": ["uuid", "uuid"],
  "geometryType": "road",
  "name": "Camino interior",
  "inputMode": "centerline",
  "widthM": 6,
  "edgeSide": null
}
```

`geometryType` accepts `road | common_area`; road accepts centerline/edge configuration, while common area accepts only polygonal sources and no road width/edge fields. The server never accepts a client union as canonical. It loads source geometries, computes source/config hashes, creates/returns one versioned `project_geometry_derivations` row and links all source rows. Derivative + sources + audit + `geometry_enrichment_jobs` commit atomically. Follow-up failure leaves `pending/failed` with attempts, next retry and repair reference; after that core commit the response is `200`/`202`, never a 5xx that implies rollback.

## 7. Replace import

`POST /api/projects/{projectId}/geometry-imports/{importId}/replace?expectedSourceSha256={hex}&confirm=true`

Requires `Idempotency-Key`, explicit confirmation and multipart with exactly one bounded `file`; project/current import, expected hash and effective `canonical_geometry_import` control are authorized before opening the stream. OFF returns `FEATURE_DISABLED`. The new file is parsed and stored through the private gateway within the same limits before the short DB transaction. The RPC locks the project/current import and then, atomically:

1. verifies `importId` is still the sole active import and its hash equals `expectedSourceSha256`;
2. snapshots every old geometry↔lot link into `geometry_assignment_history`;
3. marks old import/geometries/derivations `superseded` and detaches both `geometries.lot_id` and `lots.geometry_id`;
4. inserts the new import/features as the sole `committed/active` set;
5. invalidates calculations/readiness/documents and creates reconciliation findings/jobs;
6. records idempotency result and audit with old/new IDs.

This ordering satisfies the immediate unique-active-import constraint. New features remain unassigned until explicit reconciliation; exact matches may be proposed but are never silently applied. Ambiguous assignments are `production_readiness_findings`, not guessed. Same key/payload replays the original response; stale expected hash/racing replacement returns `409 IMPORT_VERSION_CONFLICT`. A content cycle A→B→A creates a third import version, reuses A's immutable source bytes and preserves both supersession edges. A failed DB commit leaves the old import active and records/cleans the newly uploaded object deterministically.

## 8. Unassign/recalculate

- unassign takes `projectId + lotId + geometryId + Idempotency-Key`, locks both directions and leaves the canonical geometry unassigned; it does not delete source evidence;
- recalculation takes project/version and is admin/service-only, idempotent, tenant-scoped and returns per-lot durable status;
- current unscoped GET/DELETE onboarding routes must adopt the same auth/workspace checks.

## 9. Stable errors

|        HTTP | Code                         | Meaning                                                      |
| ----------: | ---------------------------- | ------------------------------------------------------------ |
|         400 | `INVALID_GEOMETRY_FILE`      | malformed archive/KML/GeoJSON                                |
| 401/403/404 | shared security codes        | per security contract                                        |
|         409 | `IDEMPOTENCY_CONFLICT`       | key reused with other payload                                |
|         409 | `LOT_GEOMETRY_CONFLICT`      | lot or feature already assigned                              |
|         409 | `IMPORT_ALREADY_ACTIVE`      | replacement action required                                  |
|         409 | `IMPORT_VERSION_CONFLICT`    | active import/hash changed during replace                    |
|         422 | `PROTECTED_FIELD`            | strict project update violation                              |
|         422 | `PROJECT_LOT_COUNT_LIMIT`    | total_lotes is not an integer in 1..100                      |
|         422 | `GEOMETRY_SCOPE_MISMATCH`    | source/project/lot mismatch                                  |
|     413/429 | limit code                   | resource/quota exceeded                                      |
|         503 | `CORE_OPERATION_UNAVAILABLE` | no core commit occurred; retry with the same idempotency key |
|         503 | `FEATURE_DISABLED`           | canonical import control is OFF/fail-closed                  |

## 10. Required tests

- fail each project/lot insert and assert zero partial core rows;
- 20 same-key creates => one project/N lots; changed payload => conflict;
- four accepted features => four canonical rows before and after assignment;
- 20 concurrent assignments => one active geometry/lot and consistent reverse FK;
- infrastructure union keeps source count and one derived segment;
- every limit boundary and zip/XML bomb fixture;
- actor/org quota under concurrency;
- replacement invalidates downstream readiness without deleting evidence;
- `GeometryUploadPanel` uses only the canonical project-scoped route; the legacy route/source string is absent;
- rollout OFF/resolve error reads zero multipart bytes and never calls the legacy writer; scoped ON enables only the intended tenant/project;
- mass-assignment attempts over every protected field;
- Storage/metadata failure injection and durable repair.
